# ninsei architecture

Where things live and how they connect. The short rules are in [`CLAUDE.md`](../CLAUDE.md); this is the tour behind them. The code is the truth: when this disagrees with it, fix this.

Rust workspace: `crates/core` (pure rules, no egui), `crates/term` (the terminals' line editor) and `crates/app` (eframe/egui + egui_dock).

## Core and app

- **Core never imports egui.** Rules, generation, BBS navigation and ANSI parsing live in `ninsei-core` and are tested headlessly. The app sends `Action`s to `Game::apply` and renders state; panes push requests and never mutate the game while drawing.
- **Tests for UX.** What a screen shows (searches, filters, layouts, wording, what's reachable) is decided in core and tested there. How it behaves (focus, keys, clicks, what opens where, what a button sends) is tested in the app, headlessly: run frames on an `egui::Context`, feed key and pointer events, and check the state. `home.rs`'s and `liza.rs`'s tests are the pattern.
- **Native and browser.** No `std::time::SystemTime`, threads, files or `std::process` in code the web build reaches; gate native-only code with `#[cfg(not(target_arch = "wasm32"))]`.
- **Browser keys.** F5, F6, F7, F11 and F12 belong to the browser. `web/index.html` blocks the defaults of F1, F3 and F10 so the suite's legend can use them; add a key there before using it. AnarchyOS uses Esc as its leader, never Ctrl/Alt shortcuts. Chrome never gives a page Ctrl+W/T/N, so each needs another key.
- **A modal owns the keyboard.** Windows that take keys (BBS, talk) ignore input on the frame they open and call `stop_text_input` so the terminal can't eat their keys.

## Data and validation

- **Content lives in `data/`.** Warez, ICE, loot, BBS files, networks, tools, starts, themes, displays, patterns, sounds, intros and stacks. `Data::validate` must catch any bad cross-reference.
- **Balance numbers** live in `crates/core/src/tuning.rs`. The `runs_always_end` test fails if a dumb bot always or never wins.
- **Programs.** A program's stats come from its 32-byte binary (`crates/core/src/binary.rs`), never from `WarezDef` after creation. A slot never holds an invalid binary: `Action::Patch` runs `binary::check` first. Every factory program must fit the budget rule; `Data::validate` enforces it. Programs are tracked by `Slot::uid`, not index, wherever the UI holds on to one across frames: trades and sales reshuffle the HDD.
- **Two signing keys.** In a run, binaries are signed with the run's key (`Game::key`); in the stash, with the save's key (`Save::key`). Programs are re-sealed whenever they cross between home and a run (`Save::kit`/`Game::start` on the way in, `Save::record` on the way out); nothing else may re-sign a binary except optimize.

## The probe

`crates/core/src/probe.rs` drives bots through `Save::dial`, `Game::apply`, `Save::record`, `Save::buy` and `Save::wardial`, never a model of the rules. In fights a bot only drives the deck's program, in the game's BASIC: it applies `Action::Play` (which runs a line) and `Action::Finish` for the rest of the turn, then `Finish` a turn at a time while it runs, and ends the turn when the program hands it over (a STOP or a hang); the dumb bot's program is `probe::DUMB` (two lines of icepick), the careful one's is `probe::CAREFUL` (`Bot::program`), its own and not the kit's `SAFE`, which only defends; career saves start with it. Its runs: spot checks per tier (a dumb bot and a competent one) and careers from a fresh save (climbing tiers, shopping in RIG, wardialing, and buying a bigger deck when every core line is full on its chassis: the cheapest model that takes one further, read from `DeckDef::stats`, never an id). The report shows the CPU ceiling at each checkpoint, decks bought, tier-3 exits by the deck's CPU ceiling, and when the rig was maxed. `Probe` is resumable (`step` plays a few runs) so the home Shell's `probe [careers|stop]` can run it a little each frame in the browser; the CLI is the `balance` example (`cargo run --release -p ninsei-core --example balance [careers]`, `--kit <id>` plays careers from another starting kit via `Probe::with_kit`). Same seed, same report, and its lines fit the Shell. When the game gains a way to progress (a shop, a source of numbers), teach the career bot to use it, or the probe stops telling the truth.

`Game::history` (`crates/core/src/history.rs`) is filled by `Game::apply` from before/after snapshots: samples per action, trace per hop, the fight's ICE strength and turn rows, programs run, the ICE met (`History::met`, booked to `Save::ice_seen`). It never changes play, so the probe must not move when history changes.

## Theme, display and glitches

- **Themes** are `data/themes.ron` (`Data::validate` checks them). One theme (`Save::phosphor`) colours both the desktop and runs; every theme must work in both. In a run that's the `Palette` (`crates/app/src/theme.rs`); on the desktop it's the `Desk` palette register in `home.rs`, loaded each frame from the desktop theme and read through `backdrop()`/`ink()`/`shadow()`/`accent()`/`muted()`/`fill()`. The BBS window's true CGA colours and the crash screen's red are the only hard-coded colours.
- **The CRT** is a shader with data presets. `crates/app/src/crt_gl.rs` is one glow `PaintCallback` over the frame (copy, burn-in, CRT pass); presets live in `data/displays.ron` (`DisplayDef::validate`, values 0..=1, theme must exist). The glass geometry is `display::screen_to_content` in core, and `raw_input_hook` maps pointer and touch input through it, so the shader and the hit-testing must use the same curve: change both together. If the shader fails to start, `crt.rs`'s flat overlay is the fallback.
- **Damage glitches** are visual only. Core gives the level (`glitch::level`, `Game::glitch`), the last hit (`History::last_hit`) and width-keeping text corruption (`glitch::corrupt`); the app (`crates/app/src/glitch.rs`) scales a *copy* of the CRT preset for the shader (plus `u_tear`), draws the hit flash and the no-shader fallback, and hands the corruption rate to the panes, which only garble log text, never meters or numbers. The mouse keeps the preset's geometry, flicker stays capped (`glitch::tune::FLICKER_MAX`), and `Save::glitches` (on, reduced, off) is honoured everywhere. All strengths live in `glitch::tune`.

## Hardware: monitors, decks, firmware

Monitors and decks live in `data/hub/hardware.ron` (`HardwareDef::validate`); what you own and what's plugged in are on `Save` (`monitors`/`monitor`, `decks`/`deck`/`firmware`), fixed up by `Save::ensure_hardware`. The monitor picks the CRT preset (`Save::display_id`) and, if mono, locks the theme: any theme change goes through `Save::theme_blocker`. A deck's firmware is built from named parts (`netview::MapView`, `hardware::Chrome`, `hardware::Desktop`, and a sound pack); read the active one with `Save::firmware_def`, and add a new look as a new part (enum variant + renderer) that firmware entries can name, never as a special case on a deck id.

**The deck is the chassis.** A deck's `stats` rows (`hardware::StatDef { line, base, max }`, read with `DeckDef::stat`) say, per RIG line (CPU, RAM, HDD, Integrity), what it ships with and the most that line can reach on it; Stash is home storage and never a row, and every deck lists the same lines (`HardwareDef::validate`). A line a deck doesn't list falls back to its `tuning.rs` constant with no ceiling (`Upgrade::fallback`, the only reader of those constants). Home reads them through `Save::stat_base`, `stat_cap` and `stat_value` (base plus RIG, up to the cap); `Save::kit` hands the run the totals and a `Caps`, which `Game::start` puts on `Deck::caps`, so nothing in a run reads `Data::hardware`. The cap holds in three places: at home `Save::upgrade_blocker` refuses a RIG level past it, with the deck's name and the bank untouched (`Save::buy` and the magazine's `order_blocker` both ask it; the magazine still lists the line at its price, because it doesn't know your rig); in a run `buy_blocker` refuses a BBS deck mod past it before charging; and `Game::grant` clamps loot to it, logging a Sys line when nothing fit. An old save on a deck below its RIG levels keeps what it bought and runs at the cap. System's Overview shows a capped line as "value of cap" with no next once it's full. A model is one entry; a brand's models share its firmware and art and differ only in price and stats. Moving to another model of the same brand keeps the firmware you run (`Save::use_deck`), and the layout with it.

## Home: the hub, desktops and tools

- **The save** (`crates/core/src/hub.rs`) is one versioned RON document; new fields get `#[serde(default)]`, and an unreadable save starts a fresh hub.
- **The hub's rules live in core** (`hub.rs`: save, screen flow, Shell commands); `workbench.rs`, `tiling.rs` and `crash.rs` only draw and route input. Desktop icons are pixel art in `data/hub/icons.ron`.
- **Desktops are front-ends on one home.** Each deck firmware names a `hardware::Desktop` (the deck's OS, named by `Desktop::name`: `Tiling` is AnarchyOS, `Workbench` is Desktop, `Liza` is Liza). `crates/app/src/home.rs` owns everything they share (the Shell, the tool bodies, the dial and scan clocks, `WbOut`); a desktop implements `DesktopView` and is listed in `Desktops`, so a new OS is a variant, a renderer and a registry entry. Layout and focus rules live in core (`desktop.rs`, e.g. `Tiling`, `desktop::search`) and are tested there; the tiling layout is saved on `Save::tiling`, each workspace with a `desktop::Shape` (`#[serde(default)]`): full screen (`Tiling::toggle_full`, Esc `f`; only the focused tile is laid out, over the whole workspace) and the master's share in whole percent (`Tiling::resize_master`, Esc `[` and `]`, `MASTER_MIN` to `MASTER_MAX` in steps of `MASTER_STEP`). Tiles are matched to their place on the workspace by tool, never by layout index. The leader consumes a key it acts on (press, release and text) before any tile draws. **Esc drops egui's focus, and a key that closes the leader, launcher or help must not be typed into the Shell:** AnarchyOS asks the Shell for its focus (`Home::focus`) on the frame *after* it goes from not taking the keys to taking them (leader, launcher or help closed, or focus moved onto it), and the Shell takes no keys while the first-boot help is open. The help closes on a click or any key but `?` and `/`; Esc on the first-boot help closes it without opening the leader.
- **Add-ons are data.** Desktop upgrades live in `data/hub/desktops.ron` (`AddonDef`, validated in `Data::validate`), each with an `AddonEffect`; owned ids are `Save::addons`, bought with `Save::buy_addon`, read with `Save::has_effect`. A new upgrade is a new effect plus its use in that desktop's renderer, sold in RIG for the desktops your decks run.
- **Hub tool windows** (`hubtools.rs`) never touch the save directly: they emit `WbOut`s that the app applies through `Save`'s methods.
- **System is the settings app** (it replaced Prefs; `Tool::System`, `open prefs` still opens it). What its panels report is worked out in core (`crates/core/src/system.rs`: `system::overview` gives the OS, deck, firmware, each spec with its level and next upgrade, and installed tools with their `version` from `tools.ron`, then each owned copy of a game by its label, with the version from `games.ron`), tested there. Each desktop wears its own look, picked from the firmware's `Desktop` in `crates/app/src/system.rs`: Liza a System 6 Control Panel (the panels in the Liza kit's list box, the open `system::Panel` on the right, its switches the kit's check boxes and radio buttons), Desktop Workbench 1.3 Preferences (the Workbench kit's toggle gadgets across the top, solid-colour map), AnarchyOS a keyboard-first text-mode TUI (`crates/app/src/system_tui.rs`: written on the kit's `Sheet` and painted in its own 13pt type, tabs on 1-4 and `[`/`]` (never Tab, which moves the focus), neofetch About with the OS logo from `data/hub/fetch.ron` (`system::FetchDef`, `system::logo`), a text block map; every key has a click, keys live while the tile is focused via `SystemUi::keys`). All send the same `WbOut`s. Only the software you own is listed. **Disk** (`system::Panel::Disk`, it replaced STASH; `open stash` opens it) is the loadout as a block map: core's `disk.rs` works out what's installed in load order (`disk::installed`, the same programs `Save::kit` loads), the box beside it (`disk::shelf`), the map (`disk::map`, `BLOCKS_PER_SLOT` blocks a slot, display only), the RAM strip (`disk::ram_preview`), and `Save::install`/`remove`/`install_blocker`, all tested there; each kind's fill is data (`data/hub/disk.ron`, patterns from `data/patterns.ron`). **The loadout is remembered:** `Save::kit` passes each program's stash id (`Kit::origins`), the run keeps them (`Game::from_stash`, by slot uid), the exit's picker starts from `Game::loadout_keep`, and `Save::record` brings a kept one home under its old id so it stays installed; what didn't come home drops off `loadout.stash`. Tested in `crates/core/tests/loadout.rs`. **Fragmentation is saved** (`Save::disk_map`, block by block; empty means end to end): `disk::layout` keeps programs where they lie and gives new ones the first free blocks, `disk::fragmentation` is the share of split programs, `Save::fragment` scatters them (the hook for ICE that fragments your HDD, #125), and Defragment plays `disk::defrag_steps` (one swap a frame, paced by `system::anim`, display only) then `Save::defragment`.
- **Tools are downloaded, never built in.** Desktop tools live in `data/hub/tools.ron` (`ToolDef`, ids in `data::TOOLS`); a board sells one as `Drop::Tool(id)`, and an `always: true` area stocks every file with no roll (it never touches the RNG). Owned tools are `Save::tools` and `Game::tools` (from `Kit::tools`, plus downloads, booked by `Save::record` even on a flatline). Until owned, a tool isn't there at all: no icon, menu item, tab, pane or command, and no hint from the OS (`Save::opens`, `Save::has_tool`, `Game::has_tool`, `command::parse_in`/`verbs`/`help`, `hub::shell` and `shell_complete`). Only the boards' textfiles (`Drop::Text`, read on a `Screen::Read`, lines in the board's `texts`) say where to get them. A textfile downloaded from its Read screen goes on `Game::texts`/`Save::texts` (`Save::keep_text`).
  - The QWK reader (`crates/core/src/qwk.rs`, `qwk::Reader`, drawn by `bbs_view::paint_screen`, the one 80x24 terminal painter, on the kit's `Cells` at 13pt with 15px rows, runs of glyphs through `Cells::run` and block art through `Cells::block`, in `Tool::Qwk`'s window) lists each known board's bulletins and kept textfiles, 78x24 like a BBS screen (`every_reader_screen_fits_the_terminal`).
  - The ICE database (`crates/core/src/icedb.rs`, drawn by `hubtools::icedb` in `Tool::IceDb`'s window) reads `Save::ice_seen`.
  - **The phone tools, one per board tier.** CarrierTerm (`hubtools::carrierterm`) is a plain directory with a splash (`data/intros/carrierterm.ron`, a `tagline` instead of greetz, played by `Home::splash_gate`): boards and networks listed, searched, filtered and stepped through by core's `directory.rs` (tested there), a card per line with a big Dial/Call button, and a dialing card with Hang up (`Home::dial_cut` cuts the modem). NiGHTCOMM (`Tool::NightComm`, the `nightcomm` tool from Dead Sector) is the hacker's dashboard, btop on a cell grid (`nightcomm_view.rs`, drawn with `cells::Cells`: whole cells, box titles cut into borders, key hints in the bottom border): heat and each number's last results (`Entry::last`), a wardialer with a block map (`Save::finds`, booked by `Save::wardial`; it replaces CarrierTerm's WarDial tab and needs no WARDIAL, `Save::can_wardial`) and the ranges you know, and TERM, a Hayes terminal on `ninsei-term`'s `LineEditor` (core's `at.rs`: `at::parse`, `at::run` turns a line into reply lines and an `at::Effect` the app carries out through `WbOut::At`; `Save::atdt` dials one number by hand, billed `Save::call_price`, answering exactly as its block would in a scan because `dial_block`'s draws never depend on what you already know); what it shows is worked out in core's `nightcomm.rs` and tested there. The Shell's `phonebook` shows heat only with it. Tier and traits are Tiger Team Pro's (`Tool::TigerTeam`, the `tigerteam` tool, a site licence on CorpLink), the corporate audit suite drawn as a Turbo Vision application (`tigerteam_view.rs`: a menu bar of sections, a double-framed window with a drop shadow, a status line; `Cells::vision` squares the corners and sets titles in the border). It does everything NiGHTCOMM does (`Save::has_dialer`; its Reconnaissance, Address Space and Console are NiGHTCOMM's pages, `nightcomm_view::{wardial, ranges, term}`, in its frame, with their own state on `TigerTeam::nc`) and writes up each number in core's `tigerteam.rs` (`tigerteam::profile`: tier, layers, ICE, trace, pay, board; each trait's `finding` and `severity` from `networks.ron`; an `Exposure` rating), tested there. The Shell's `phonebook` shows tier and traits only with it.
  - Text-mode tools lay out on the kit's `Cells` (`crates/app/src/kit/cells.rs`), never egui spacing. Desktop icons that don't fit one column start another (Liza's to the left, Desktop's along the right edge).
- **The kit** (`crates/app/src/kit/`) is the one layer every fake app draws with. Its text-mode parts (`cells`, `list`, `fit`, `sheet`) own geometry and behaviour and leave the look to the caller; a desktop's GUI idiom is that desktop's parts, drawn to its spec sheet in `docs/refs/`: `anarchy` (AnarchyOS: tiles, the bar, the launcher, the help; `docs/refs/anarchyos.md`) and `liza` (System 1: the window frame, the menu bar and menus, the scroll bar and its scrolled view, the list box, push buttons with the default ring, check boxes, radio buttons, and HyperCard's text field, pop-up menu and dotted drop slot, in a `kit::liza::Look` of the theme's ink and paper and the patterns; shared by the Liza desktop, System's Control Panel and the Stack chrome's Script card; `docs/refs/liza.md`) and `workbench` (Workbench 1.3: the screen's title bar, the window frame returning its close and depth gadgets' rects so the hit tests share them, the proportional gadget a window scrolls with, the 1.3 bevel, push buttons, toggle gadgets and the requester, in a `kit::workbench::Look` of the theme's colours; shared by Desktop and System's Preferences; `docs/refs/workbench.md`). What their scroll bars share (where a view stands, the thumb, paging and dragging, the wheel only when nothing covers the bar, a view scrolling beside the desktop's own bar) is `kit::scrollbar`. Either way every colour comes in from the theme, and **nothing in it names a tool or a deck** (a widget that only works by checking which app draws it belongs in that app's renderer). New screens use the kit, and a touched screen moves onto it.
  - `cells.rs`: the cell grid (`Cells::fit` in the app's monospace cells, or `Cells::sized` in a face's own font and row height, and `Cells::allocate` to take a face's room and its cells in one measure; `cell_at` is the inverse of `at`, for clicks; `fit_font` fits a font's grid to an area; `at`, `text`/`text_max`/`text_right`, `fill`, `inverse` for a selected row, `frame`, `boxed`, `title`, `frame_double`, `meter` and `meter_in`, whose unlit cells take a colour so a meter on an inverse row stays visible, `block` for block elements painted as solid parts of a cell, and `run` for a run of ordinary glyphs as one piece of text, for a screen that repaints every frame, and `gauge` for a meter with a count of cells lit (a part cell at the edge; a whole count lights them exactly) coloured by index, its unlit cells an outline or a dot; `title` turns into a top edge and `note` up into a bottom one), and `cut`, a string cut to n cells with `…`, and `cells_in` (the whole cells a rect holds).
  - `sheet.rs`: `Sheet<C>`, a character grid written first and painted after, for a face whose height comes from what it holds (it scrolls in its window): `put`, `inv`, `key`, `rule`, `stamp` (a narrower sheet, for wrapped text) and clickable runs (clamped to the sheet, their ids salted with the sheet's own room) that come back as `C` and are widgets labelled with their text, so tests and screen readers find them. Text past the edge ends in `…`. System's text face is written on one.
  - `anarchy.rs`: AnarchyOS's GUI kit, after Omarchy/Hyprland, to the spec sheet `docs/refs/anarchyos.md`: `tile` (the frame, the focus border, the label cut into the top edge) and `tile_content`, `bar` (workspace pills, the mode, the focused tile, the widgets; it reports the pill clicked), `launcher` (the search box and its list: whole rows on whole pixels, scrolling on `List` with the pick and the wheel, a muted `3/19` when it runs past the box; the search is handed in, so core's `desktop::search` stays the rule) and `help` (the key help). It takes labels, states and a `Look` (the theme's colours and type), never a tool or the save; `tiling.rs` decides what to show and what keys do.
  - On the kit's cells too: the 80x24 terminal painter (`bbs_view::paint_screen`: the BBS window, the QWK reader, the intro splash) and the hex editor's byte grid (`hexview::grid`, at 15pt with 22px rows: the offset, three cells a byte with a gap after the eighth, then the ASCII column; the cursor, the change marks and the click mapping all come from the cells).
  - `list.rs`: `List`, a list's window between frames. `List::view(len, sel, rows)` gives the items to draw by core's one scroll rule (`ninsei_core::scroll::window`: move just enough to keep the selection in view, never past the end) and `List::mark` cuts where you are (`scroll::position`: `3/40`, or `↓ 12 more` without a selection) into a box's border. Drawing the rows stays the caller's. NiGHTCOMM's and Tiger Team Pro's lists use it, and so does CarrierTerm's directory, a GUI list that draws only the whole rows in its window (`hubtools::list_box`: the arrows move the window with the pick, the wheel scrolls it a row at a time, the footer says `10/15`); there is no other scroll rule.
  - `fit.rs`: how much room a screen needs, for a screen that can't scroll its way out of a small window. A `Need` is the grids it works in (`Fit { cols, rows }`; a few, for a layout that changes with shape, and any one will do) how the face counts the cells a rect holds, in its own font (`Need::cells` for the kit's), and whether its height scrolls (then its rows are a floor and it's counted beside the scroll bar, `home::scroll_bar`). `fit::check`, `fit::fits`, and the one notice (`<tool> needs 56x12 (has 41x9)` and the desktop's hint), drawn in whole cells.
- **Tools fit their room, or say so.** `Home::fit(tool, desktop, data)` is the one place a tool's face says what it needs: NiGHTCOMM and Tiger Team Pro (cells on every desktop) 56x12 kit cells, AnarchyOS's System 40 of its own columns (its text face lays out to at least that; its height scrolls), a game its field from `games.ron` (`games_view::grids`; a `fit::Need`'s grids can come from data). GUI faces need nothing and scroll in a small window. Every desktop draws a tool through `Home::tool_in`, which checks the room and, when it's short, draws the kit's notice instead with the desktop's hint: AnarchyOS `Esc f: full screen` (only when full screen would help: not on a full-screen workspace, not for a lone tile; `full_screen_hint`), Liza and Desktop `Drag the window higher for more room.` (their windows open big enough and only shrink when dragged toward the bottom; `home::drag_hint` gives it only when the window isn't already at the top). A tool taller than its room scrolls with the desktop's `home::Scroller` when it passes one (Liza's windows: the kit's scroll bar, `kit::liza::scrolled`; Desktop's: the proportional gadget, `kit::workbench::scrolled`; each flush on the frame and only while the tool runs past the window, each window opening the bar's room wider than its tool; `every_tool_window_shows_its_tool_whole_beside_the_scroll_bar` and `..._beside_the_gadget` check no text is cut, with the harness's `cut_text`), else egui's bar in the theme's colours. No tool draws its own "too small". `every_text_tool_fits_its_tiles_or_says_so` draws each of `Home::TEXT_TOOLS` and every copy of every game, every page, at every tile the tiler makes at 1280x800 (alone, master and stack with one to three others, the master at its default, narrowest and widest share) and checks nothing is cut (at the sides only, for a face that scrolls); `the_notice_shows_exactly_below_each_tools_minimum` checks each grid a cell short either way (games too); `every_tool_window_opens_big_enough_for_its_tool` does Liza's and Desktop's windows.
  - A fresh phonebook always has the default board, so the starter tools are always reachable.
- **Games are data, and the save knows which copy you own.** Each game is a row in `data/hub/games.ron` (`data::GameDef`: name, blurb, publisher, version, a `cols`x`rows` field, a `crack` and a `splash` intro, an optional `shop` price, the `engine` it runs (`games::Engine`) and its `tick_ms`). `Data::validate` rejects a field smaller than its engine's `min_size` or past 78x24, a `tick_ms` outside `data::GAME_TICK_MS`, a `crack` that isn't a crack or a `splash` that isn't a splash, a publisher that isn't a CPU Shopper vendor, a splash whose tagline doesn't name the row's name and version, a board file naming an unknown game, and any `Drop::Game` in loot or an encounter: games only come from a board's files. Owned games are `Save::games`, one `hub::OwnedGame { id, copy }` per game and copy (`hub::GameCopy`): you can own both side by side, and neither erases the other. A `Cracked` copy comes from a board (`Drop::Game(id)`: in a run on `Game::games`, which starts from `Kit::games`, the save's cracks (`Save::cracks`), plus downloads, booked by `Save::record` even on a flatline and reported in `RunReport::games`; at home through `Save::home_buy`); a `Boxed` one by mail order (`shopper::Item::Game` in the Games section, sold by the publisher, `Save::buy_game`). `Save::learn_game` is idempotent per game and copy; `has_copy` and `copies` ask what you have. THE NEON GUTTER's GAMES area posts the three cracks (two a call, rolled like any area), each file named 8.3 with its crew's tag and only on the board its crack advertises (`Data::validate` rejects either mistake); CPU Shopper prints Paper Tiger's Box ad for BLOX 2.0 and a cover line, the other boxes as dot-leader lines. A board won't sell a crack you have (`game::tool_blocker`, which asks the `bbs::Line`: `Line::owns`, `has_crack`) and the shop won't sell a box you have, but each still sells its copy to someone holding the other. Each copy opens with its own intro and has its own label (`Data::game_label`): a box is the plain name (`Nibbler`), a crack the name in capitals with its crew's tag (`NIBBLER [2K4]`), the `tag` on its crack intro. About This Deck lists each copy you own by its label, after the tools. **The games are engines in core** (`crates/core/src/games/`): each is a pure, seeded state machine behind the `games::Arcade` trait (`step(Input, ticks)`, `cells()` row by row, `cursor`, `over`, `won`, `paused`, `score`, `status`), started by `games::new_game(def, seed, round)` from the row's `engine` (the game's id and the round go into the seed, `games::round_seed`, so each round deals a new field and no two games share a stream) (`Nibbler`, `Blox`, `Minefield`). The app only sends `games::Input`s and a count of the game's own `tick_ms` ticks and draw the `games::Cell`s; an engine never reads a clock, and the same seed and inputs always play the same game. Their speeds, points and mine density are in `tuning.rs` (`NIBBLER_*`, `BLOX_*`, `MINEFIELD_*`). Tested in `tests/games.rs`: every game ends, random input never panics or leaves the grid, same seed same game. The probe's bots value a game at nothing, so they never buy one. Tested in `crates/core/tests/games.rs`.
- **Games open on every desktop.** A copy you own is a tool: `Tool::Game(id, copy)`, one variant for every game and copy, its id carried inline (`hub::GameId`, at most `hub::GAME_ID_MAX` bytes, saved as the plain id) so `Tool` stays `Copy`. Everything a desktop shows for it reads the row: `Tool::name` (the copy's label, `Data::game_label`), `Tool::game_def`, its icon (`icon` in `games.ron`, the 1.3 palette, checked by `IconDef::check_art`), and `Tool::games(data, save)` lists the copies you own in the order you came by them. `Save::icons` is the desktop's icons (`hub::Icon`, borrowing the art: the tools you have, then each copy); `Save::opens` is false for a copy you don't have, so an unowned game has no icon, menu item, launcher entry, tile or Shell word (`shell`'s `run`/`dir` and `shell_complete` read `Save::icons`; `run nibbler` finds a game by its box's name, the label picks the copy). Liza lists the copies in a **Games** menu before Special and as icons; Desktop's `Kind` is `Shell`, `Tool(tool)` or `Requester` (no fallback: a game's window is its own); AnarchyOS's launcher has an entry per copy. Liza's and Desktop's game windows open where `home::game_spot` puts each copy, sized the first time they're drawn (`home::size_game_window`) to the field, or to the intro's 80x24 screen when that's bigger and an intro will play (`home::game_window`). The window (`crates/app/src/games_view.rs`) draws the engine's `cells()` on the kit's `Cells`, a cell two text cells wide (one in a narrow room), in a frame with the game's status wrapped under it (`games_view::status_rows`); every cell reads by its shape (fills, the `p50` pattern, glyphs, inverse) so nothing is told by colour alone. A game lives as long as its window is open: before drawing, the app tells `Home::keep_open` which tools any desktop still has open (`Desktops::is_open`: Liza's and Desktop's windows, AnarchyOS's tiles on the save; hidden, on another workspace, behind another firmware or showing the fit notice is still open), and `Home::play` keeps the copy's window state until it closes: its intro first (the crack's cracktro or the box's splash, unless intros are off; only a key or click while its window has the keyboard skips it, and the game starts the next frame so the skipping key isn't the game's; run to its end, the game starts on that frame; closing the window while it still plays cuts its tune), then one `games_view::Session`, a new round when it opens or Space is pressed once it's over. Each sends `WbOut::GameStarted(id)` so `Save::start_game` bumps `Save::game_rounds`, and `games::new_game` gets the save's key and the round: the save's count or one past the last `Home` dealt, whichever is more, so both copies opened in one frame deal two fields. It ticks whole `tick_ms` ticks on the frames' `stable_dt`; it takes the arrows, Space and P only while its window has the keyboard (`Home::tool_in`'s `keys`: each desktop's front window or focused tile while no menu, leader, launcher or help is up, and never while `Cx::keys` is false, a board called from home owning the keyboard: then AnarchyOS's leader and launcher stand down too, System is `blocked` even under the pointer, and no tool's intro is skipped), stopping text input; a click opens a square and a right click flags it. Losing the keyboard pauses it, and getting it back plays on unless the player paused it. Tested in `games_view.rs`, `liza.rs`, `workbench.rs`, `tiling.rs` and `crates/core/tests/game_tools.rs`.
- **Cracktros are data.** Each is `data/intros/<id>.ron` (`intro::IntroDef`, found by `build.rs`, checked by `IntroDef::validate`), named by a tool's `intro` or a game's `crack` and `splash`. A crack names its `board` and its `greetz`, and a game's crack its crew's `tag` (at most `intro::TAG_MAX` capitals or digits, one tag per crew); a splash has a `tagline`, greets nobody, carries no tag, and may leave the board out, in which case its screen has no ad row (`IntroDef::is_splash`); core turns time into the screen (`IntroDef::screen`: frames, `Fx` effects, the board's ad, the greetz scroller, timings in `intro::anim`), and `Home::intro_gate` paints it in the desk's colours every time the tool's window opens (a game's window plays its copy's, above), skippable, its type shrunk to the width and the height in view in a room smaller than the screen (`bbs_view::paint_screen_fit`), never cut, honouring `Save::intros` and `Save::glitches` (calm). Its chiptune is an `intro::TuneDef` (tracks of note steps, `TuneDef::render`, synthesized like cues); the speaker plays it on the music channel it shares with the run's tune (`Speaker::tune`), cut when the intro is skipped or its window closes (`Home::tune`, `TuneCue`). The speaker knows which of the two is on, so an intro closing as you jack in can't cut the run's tune, and the run ending can't cut an intro.
- **Stacks are data.** HyperCard-style stacks (`crates/core/src/cards.rs`) are cards of text and 1-bit pictures; **Welcome to the Net** is `data/stacks/welcome.ron` (`Data::welcome`, checked by `StackDef::validate`: lines fit `cards::TEXT_COLS`x`TEXT_ROWS`, pictures exist). Card text never hard-codes a number the rules own: it uses `{placeholders}` (`cards::PLACEHOLDERS`, filled by `cards::fill` from `tuning` and data). It's `Tool::Guide`: an icon on Liza, opened on a new save's first boot (`Save::guide_seen`), and `help net` in the Shell on any desktop; `hubtools::guide` draws it.

## The shop and the books

- **RIG is CPU Shopper, and it's data-driven.** The catalog (`Save::catalog`, `crates/core/src/shopper.rs`) is everything priced in its own file: `rig.ron`, `hardware.ron`, `desktops.ron`, `panes.ron`, any tool in `tools.ron` with a `shop` block, and any game in `games.ron` with one (the Games section, sold by the game's publisher; a cracked copy doesn't count as owning the box). No game has one until games open on the desktop, so the Games section and Paper Tiger stay out of the issue until then (an empty section prints nothing). A new item is an entry in its own file and appears in the next issue on its own, as a dot-leader line in its section. `data/hub/shopper.ron` (`ShopperDef`) only dresses it (cover, sections and page numbers, vendors, ads) and never prices anything; deleting an ad drops the item back to a list line, never out of the magazine. `shopper::layout` makes the pages in core and is tested there: each block owns a rectangle of a `GRID_COLS`x`GRID_ROWS` page grid, small sections share a page, and blocks grow to fill it; `crates/app/src/shopper.rs` only draws them. Buying is one `shopper::Item` through `Save::buy_item` (and `order_blocker`), routed as `WbOut::Order`; a new kind of item is an `Item` variant plus its buy rule. Hotlines are 1-800 decoration, never 555. A tool sold with `review: true` is a test listing (tagged REVIEW COPY), and the probe's bots never buy it. Every deck has a full page (`size: Full` ad) with its hero picture (`DeckDef::art`, a 1-bit grid in `data/art/<id>.txt`, found by `build.rs` and checked by `ArtDef::validate`; replace art by overwriting the file) and, under it, the add-ons for its desktop; add-ons for an OS none of your decks run are listed with `Stock::Call` (CALL NOW) and can't be ordered. Buying a deck doesn't switch to it and buying a monitor doesn't plug it in; owned items show their price, greyed, because the magazine doesn't know your rig.
- **Books share one page control.** Anything you page through (the Welcome stack, CPU Shopper) is drawn by `crates/app/src/pager.rs`: one fixed page size (`pager::PAGE`) that never scrolls or resizes, and one bar under it (◀ Home ▶, where you are, a status) whose buttons never move and grey out at the ends; keys are ← → / PgUp PgDn / Home over the book. Turning is `book::turn` in core. A window holding a book is sized to fit `pager::SIZE` exactly. A new book is a page renderer passed to `pager::show`, never its own controls.

## Starting out, networks and phone numbers

- **How a deck starts is data** (`data/hub/starts.ron`, `hub::StartsDef`, checked by `StartsDef::validate`): every deck gets `hub::FIRST_BOARD` (Sense/Net CustomerLink: free, no tiers, never a run's board) and the `always` networks (the school net, whose board is the Gutter), plus one kit (`KitDef`: free programs, boards, starter numbers, tools, ranges, bank, and games already on the desktop: the default kit's is the shop's disk, NIBBLER cracked), applied once on a new save's first boot (`Save::ensure_phonebook`, `Save::started`) and recorded on `Save::kit`; `Save::free` is that kit's free programs. The default kit is what players get. Sense/Net's partner directory hands out the starter networks once (`Save::add_starters`, seeded from the save), and a post on it gives the Gutter's number. Two boards never share a number.
- **Networks are data.** Tiers, traits and companies live in `data/hub/networks.ron` (`NetworksDef::validate`). A trait is a `TraitEffect` that `Save::site_params` turns into `NetParams` (generation) or `RunMods` (ICE strength, trace %, pay %); add new effects there, not as special cases in the run. Default `NetParams` must keep generating the same networks for the same seed. A trait's `Shape` sets the topology (widths, cross links, chokepoints); tiers and the `Subnets` effect place subnet nodes.
- **Subnets are side trips.** Entering a `Subnet` node swaps in a smaller network (`Network::subnet`, seeded from the run and node) and parks the main one in `Game::outer`; the subnet's exit (the UPLINK) puts you back on the subnet node. Contracts always point into the main network: use `Game::root`/`root_at`, never `game.net`, for contract nodes.
- **Phone ranges are data.** `data/hub/exchanges.ron` defines ranges (`RangeDef::validate`); `Drop::Hint(range)` teaches one, from loot, BBS files or encounters, and `Data::validate` rejects hints at unknown ranges. A wardial block always answers the same way for a save (seeded from `Save::key`, range and block), so results never depend on when you scan.

## BBSes

- **Boards are folders.** Each BBS is `data/bbs/<id>/` (`board.ron` + `splash.txt`), found by `crates/core/build.rs`; nothing registers them. `Data::boards` holds them with the `default: true` board first. A run's board is `Game::board` (read it through `Game::bbs()`, never `data.boards[0]`), chosen by `Save::site_board`: a trait's `Board(id)`, else one of the boards for the tier picked by the phone number, else the default. Choosing a board must never touch the run's RNG before the network is generated.
- **Screens** are pipe-coded text, max 78x24, enforced by `every_screen_fits_the_terminal` (every screen of every board). A board's look (`Look`: header style, colour roles, wording, l33t) is data; `bbs.rs` draws with the board's colours, never hard-coded pipe codes. Boards can carry message bases (`messages`: bases of posts, `Screen::Messages`/`Base`/`Post`) and no jobs (`jobs: false`).
- **Reading opens doors.** A bulletin or post's `on_read` (`ReadEffect`: a `Board`, the `Starters`, a `Hint`) goes through core, `Action::Read(Reading)` in a run (`Game::boards_read`/`starters_read`, booked by `Save::record` even on a flatline) or `Save::home_read` from home. A cracktro is a door too: the first time an intro plays on a save, its window sends `WbOut::SawIntro(id)` (`Home::splash_gate` for a tool, `Home::play` for a game; nothing while intros are off) and `Save::saw_intro` books the board its scroller advertises, once (`Save::intros_seen`; a splash advertises none). The career bot opens what's on its desktop before its errands (`probe::open_desktop`), so the probe follows the same door.
- **A BBS session reads a `Line`.** `bbs::Session` draws and navigates through the `Line` trait: a board reached in a run (`Game`) or called from home (`home_bbs::HomeCall`). New BBS features go through `Line`, never `&Game`. From home (`crates/core/src/home_bbs.rs`): boards are learned in a run (`Game::bbs_seen`, kept by `Save::record`) or by wardialing their number (`Answer::Board`); `Save::call_board` charges `call_cost`; listings and jobs are seeded from the save's key, the board and `Save::runs`, and `record` clears what was bought or taken. Jobs taken at home wait in `Save::pending` and ride into the run on their entry's network (`Kit::jobs`), where `Game::bring_jobs` picks targets with its own RNG after the network is built. Deck mods only sell in a run.
- **l33t goes through one translator** (`crates/core/src/leet.rs`, `leet::translate`). It's one character in, one out, so layouts keep their width; it leaves pipe codes, digits, bracketed hotkeys and 8.3 filenames alone. A board with `look.leet` applies it to every screen but the splash and the modem lines; an event opts in with `leet: true`.
- **Encounters.** Every encounter needs a `Leave` choice (`Data::validate`), and `every_choice_in_every_event_resolves` must keep passing: no choice may leave the runner stuck in `Phase::Encounter`.
- **Run vs home.** In a run, `Action::Patch`/`Optimize` only work at a BBS (`Game::compile_blocker`).

## The run screen

- **Chromes are plug-ins.** A firmware's `hardware::Chrome` picks how the run screen is dressed; `crates/app/src/chrome.rs` maps it to a `ChromeView` (`chrome::view`): one method per pane, plus tab titles, menus (arranged from shared `MenuPart`s), the status line, an optional bar over the panes, under the menu bar, keys, an overlay and the default layout. Every method defaults to Classic, so a new chrome is a `Chrome` variant plus a `ChromeView` that overrides only what it changes. Never test the chrome in a pane; ask the view. `btop.rs` (`Chrome::Btop`), `suite.rs` (`Chrome::Suite`, the Hosaka) and `stack.rs` (`Chrome::Stack`, the Sense/Net: HyperCard, 1-bit; `ChromeView::one_bit` keeps glitches from splitting colour, `ChromeView::palette` folds the run to ink on paper, `ChromeView::dock_style` dresses the panels as HyperCard windows, and its **Script pane** is the **Script card**, on screen the whole run beside the ICE card: `ninsei_core::stack_fight::card` decides it (with `Card::fighting` and `Card::budget_words`: the budgets left this turn in a fight, the deck's limits a turn outside one, where Step, Run and Pause stay greyed; `Card::broke_words`, a hang's `?BREAK IN n` at the title line's left) (the program's lines as `Block`s with their `Field`s, pop-up menus that list only the disk and number fields, the ▶ on the line about to run, which of Step, Run and Pause can be pressed, and the budgets in words), and `stack_fight::{set_field, add, insert_before, remove, swap}` turn an edit into one `Action::Program` with one line rewritten, so the card holds nothing of its own; `stack.rs` only draws it with the Liza kit (`popup_menu`, `text_field`, `dotted`, `push_button`), scrolling rows of their own heights a whole row at a time, a palette chip clicked or dragged (egui's drag and drop, `BlockKind` the payload) to add a block, a click on a block selecting it (view state in egui memory, by line number, dropped when the line goes) for the palette's move and clear boxes (`stack_fight::moved_to` says where a moved block lands, so the selection follows it), the Deck card's bars sized to the column (`bar_width`), and its keys through `ChromeView::keys` before the shared hotkeys: Enter presses Run, Esc pauses a running program and never closes anything) are the three so far; the suite's Script pane is the **`PROC-7.BAS` Module window** (`suite_script`): Turbo Debugger's listing over a Watches strip in one `suite::window_with` (its double rule lit while active, `CPU 3/3  RAM 6/6` in its bottom edge, a hang's `?BREAK IN n` before it), from core's `suite::{module_mark, module_note, watches}`; its F3 Insert and Backspace open and delete a line on a keyboard with no Ins or Del; a click on its legend gives the window its keys back the next frame (and F2 or F3 there opens the retype then), and while a line is retyped the window stays active and no F-key acts; F-keys act on a fresh press, never a repeat; the steps of a pass the interpreter says (IF, GOTO, STOP, a break, the end of the turn) are `LogKind::Program` lines, filed as `PRG` in its activity log, and a RUN's row is the program's own (`OK`, `MSG` or `ERR`); the suite's rules (sheet sorting, formulas, axes, work-order totals, dialogs via `suite::Watch`) live in core's `suite.rs`. Both text decks' Script panes are **listings** on the kit's `kit::listing::Listing`, decided by core's `listing` (rows with their gutter marks and faults, which debugger and editor keys press, the cursor's home and moves, a new line's number through `basic::Program::free_line_between`, and every edit as one `Action::Program` with one line rewritten): the listing keeps the pane's focus id and view state (cursor, a `kit::List` window, the line being retyped), takes its keys through a deck's `Bind` table, drops the typing the pane holds the keys for, and puts a `ninsei_term` line editor over a retyped row; each deck only draws the rows in its look and names its keys. The btop chrome's **Script pane** is the **`ice.bas` tile** (`btop::script`), on screen the whole run in the right column of its three-column default layout (deck.sys over warez/, the map, `ice.bas` in front of todo, over the terminal; `chrome::three_columns` lays that shape out for every deck, each passing its `Shares`): btop's words come from `ninsei_core::btop_fight` (`TITLE`, `note`: `cpu 2/3  ram 6/6`, the deck's limits outside a fight, a hang's `?break in n` before it; `mark`: `▶` and `●`; `legend(&Keys)`: the two rows of keys at the tile's foot, lit while they press), and the rest from core's `listing`. The tile draws inside `Listing::show` in a `btop::boxed_lit` box (its border lit while it has the keys) and binds its letters through `Listing::keys` (`r s c p`, `j k` or the arrows, `e`/Enter, `o`, `d`, Esc), read in `ChromeView::keys` before the shared hotkeys and only while it has the focus; `ChromeView::script_has_keys` tells the shared hotkeys a pane holds the keys without typing, so Space and the digits still work the hotbar. The btop chrome (`crates/app/src/btop.rs`) keeps its timings in `btop::anim` and colours its gradients with `btop::ramp` (`faint → dim → fg → bright`); dot-graph maths is `history::plot`, tested in core; the font has no braille, so the app paints the dots. Both chromes lay their frames out on the kit's cells in their own 12pt type: btop's boxes (`btop::boxed`: the border through the outer cells, the title turned into the top edge `┐title┌` and a note turned up into the bottom one `┘note└`, both cut with `…` to fit, the body 10px and 12px inside the line as before, and always drawn, however small the box) meters (`Cells::gauge` with dotted unlit cells: a little thinner than the old meter and square-cornered, the kit's cell) and the warez table, whose NAME is as wide as the widest real name, dropping CPU before it would slice one; the suite's document window (`suite::window`: the kit's double frame with `[■]` and `[n]` set in its top edge, a heading row only for a document's own title, never repeating its tab, a 5px shadow, and the body always drawn), its status line and F-key legend (one-row kit sheets), its dialogs' bodies (a sheet, lines wrapped), its activity log (whole rows of cells through `ScrollArea::show_rows`, only the rows in view painted), and its spreadsheet, whose columns come from core's `suite::sheet_widths` (each its widest real value and its header with a sort arrow, a cell of padding either side), so nothing is cut at a clip rect.
- **The sound pop-out is the chrome's.** Every run screen has one control for the sound: the level (`Save::volume`, a percentage, full by default) and the switch (`Save::sound`, the same one the System app shows). `crates/app/src/volume.rs` holds what's shared: `volume::Level` read from the save, `volume::Popup` (open, and what was set when it opened, so a Cancel can put it back), `Level::to` turning a change into `Request::Volume` and `Request::SoundOn`, and `volume::start`/`volume::keys`, which take the keyboard from the command line while it's open (the run's hotkeys, the chrome's keys and the terminal's focus all stand back; however it closes, the command line gets the keys back). It never opens over something that already has the keyboard (`App::modal_up`: a BBS, a conversation, a suite notice), and one of those coming up closes it. `volume::hit` names a control drawn in cells or pixels. The chrome opens and dresses it: a `MenuPart::Sound` item worded by `ChromeView::sound_item`, and `ChromeView::sound`, drawn over the overlay while it's open. The classic default is a small window with a slider; btop puts a bar-module speaker in its status line (`ChromeView::status_extra`, which gets a `FrameCx` and returns requests) that opens a box of whole cells over it; the suite has Edit > Sound..., a dialog with OK and Cancel, drawn by the same `suite::dialog` and `suite::buttons` as its notices; Liza has View > Control Panel..., the Mac's Speaker Volume slider (0 to 7) and a Sound box in a striped window (`liza::window_frame`). Notches map to the level through core's `hub::volume_notch` and `hub::notch_volume`. The pop-out only pushes requests; `main.rs` applies them to the save and the speaker.
- **Panes are modular, and secondary panes are owned.** `panes::Tab` lists every pane: `Tab::CORE` are always there; `Tab::SECONDARY` pairs each extra pane with its id in `data/hub/panes.ron` (`PaneDef`). A secondary pane is available when bought in RIG (`Save::buy_pane`, `Save::panes`) or bundled with the firmware (`FirmwareDef::panes`); read it with `Save::has_pane`. A new pane is a variant, an id, a catalog entry and a renderer, dressed by each chrome (`ChromeView::net` is the pattern). `Tab::Script` is a core pane: the deck's program, on screen from a run's first frame, dressed by `ChromeView::script` (the classic dress is the terminal's `prog` listing until a deck designs its own; the Stack's is the Script card, below under Chromes). The two secondary panes so far are `net` (traffic, bundled with Cyberspace 7.0) and `vis` (`Tab::Vis`, sold only): what the speaker is playing, from `Panes::hear`, which calls `Speaker::listen` only when a vis pane is drawn (a tab behind another one never asks), and `vispane::alive` asks for frames only while something is heard. It never reads the game. The maths is core's `scope.rs` (a Hann-weighted radix-2 FFT into bars spaced evenly in pitch, levels in dB, and `ballistics`: bars jump up and fall at `FALL_PER_SEC`). `vispane.rs` has the shared parts: the trace, `bars` (asks for frames only while a bar is still falling, so silence is still), and `held` (numbers take a new reading every `HOLD_SECS`, so they never strobe). btop draws a box of cell columns (`Cells::meter_up`), the suite a SOUND LEVEL REPORT (a form and a band chart in dB), and the Stack chrome (the Sense/Net) a 1-bit Scope card with a dotted ink graticule. The default layout is the chrome's (`ChromeView::default_layout`) with the panes the player has; the player's layout is saved per firmware (keyed by maker and firmware id, so it follows a brand's models) in `Save::layouts` as opaque RON the app writes (`Save::set_layout`/`layout`, core never parses it). Anything that won't read back or lacks a core pane falls back to the default, and panes the player doesn't have are dropped (`parse_layout`).
- **The network map has three views.** `crates/app/src/netmap.rs` holds what they share (fog, targets, tags, clicks, the hint) and hands off to `netmap_iso.rs` (wireframes over a grid), `netmap_draft.rs` (a flat technical drawing) or `netmap_paint.rs` (a 1-bit picture, nodes filled with patterns from `data/patterns.ron`, two colours only), picked by the deck's firmware (`Save::firmware_def(..).map`). Shapes, symbols and paint fills per node kind are data (`data/netmap.ron`, `MapStyleDef::validate`, paint fills checked against the patterns); meshes, the isometric camera (`Iso`) and node placement (`netview::flat_layout`) live in core (`netview.rs`) and are tested there. Map colours come from the palette: grid `faint`, wires `fg`, fills `dim`, highlights `bright`. Map animation (derez bursts, the jack-in sweep, trace pressure, hover) lives in `netmap::Anim`, remembered in egui's memory rather than the game, with every timing in `netmap::anim`; the hop trail comes from `Game::travelled`.
- **Fights have a view; the preview is the rule.** `Game::preview(slot)` (`crates/core/src/fight.rs`) says what running a program would do now or why it can't, and `Action::Run` resolves through it, so a hint can never disagree with what happens. Nothing loads: every program on the HDD can run (`Slot` has no loaded flag, warez have no RAM cost, binary byte 07 is reserved, and the hex editor's budget is `BUDGET_PER_CPU * cpu + BUDGET_PER_OPT * opt`).
- **Fights run a program** (design: `docs/design.md`, "Fights: the deck runs a program"). The language is `crates/core/src/basic.rs`: `basic::parse` turns text into a `Program` of numbered `Line`s (`Stmt::Run`, `If(Cond)`, `Goto`, `Stop`, `Rem`, and `Bad` for a line that doesn't parse, kept and skipped so a typo never halts a fight; `Program::fault` names what's wrong, a GOTO to nowhere included; text with no line number is `Program::stray`, kept as typed and never run), `Program::text` prints it back, `set_line`/`remove` edit it, and `basic::names` says what a program name in a RUN or HAVE matches (name, file name or factory id), for fights and validation alike; it knows nothing of a fight. The deck holds one program: `Save::program` (`None` until a run ends: the starting kit's, `StartsDef::program`, where a kit without one ships the default kit's, read with `Save::program_text`; `Data::validate` rejects a kit program with a bad line or a RUN or HAVE naming no warez through `hub::program_fault`), handed to the run as `Kit::program`, parsed into `Game::program` and written back by `Save::record` however the run ended. `Game::exec` (`Exec`: an `ExecState` of `Paused`, `Running` or `Stopped(line)`, `pc` the line about to run, this turn's pass as `Step`s, the lines it has `visited` since its last RUN, `open` while a pass is under way this turn, and `broke`, a hang's line) is reset at each fight's start with the cursor on the first line. `Game::line` is the only place a statement executes: it runs the line at `pc` (passing over REMs on either side, so the cursor never rests on one), starting a pass from the top when none is open, and returns a `Line` (`Went`, `Stopped`, `Hung`, `Ended`, `Over`). A pass runs until the program ends, a STOP, the cycles run out or `Combat::ifs` (one GB of `deck.ram_max` per IF evaluated, reset each turn) is empty, and the line that gets there ends the turn there and then (`Action::EndTurn`, which closes the pass: `open` off, `pc` to the first line); each RUN finds its slot by name (`Game::slot_named`), asks `preview`, and is applied as `Action::Run`, so history and cues hear each one. `Action::Step` is one `line` (gdb's `step`), `Action::Play` sets `Running` and runs one, and `Action::Finish` (gdb's `finish`, `Game::pass`) loops `line` for the rest of the turn, leaving the state as it was; the probe plays by `Finish`. Each step is said in the log as it happens (`Game::step_text`; a RUN says nothing more than the program's own line), so the pass reads before what the ICE does after it. A pass that comes back to a line without running anything is a hang: `?BREAK IN <line>`, the debugger has the turn, the turn doesn't end, the cursor stays on the line and `Exec::broke` holds it (read through `listing::broke`) until the next Step, Play, edit or the turn's end; the next line starts the pass again at the top. A false IF skips its line, and a skipped IF skips its own (two IFs in a row are an AND). The app's frame loop plays a `Running` program a line every `LINE_SECS` (`drive_program` in `main.rs`, a display number, not tuning), turn after turn; `Pause` stops it where it is, keeping `pc`, the open pass and the budgets; after a STOP (`Stopped(line)`) the next Step or Play carries on past it in the same turn; `Program(text)` replaces the program at any time (after a STOP it carries on from the first line past it, paused partway through a pass from the line it was on), and the hotbar's `Action::Run` works whatever the state and leaves `pc` alone. Views read `Game::program_view` (each line's text, the current line, STOP and fault marks, the budgets left, the pass, whether one is `open` and a hang's `broke`) and `Game::step_text` (a pass's step as the OS says it, a sentence per line), and `Game::ifs_left` for the RAM meters. The run terminal drives it (`command.rs`: `prog` lists, through `command::listing`, `prog <n> <line>` types a line in, `prog <n>` deletes it, and `step` (a line), `finish` (the rest of the turn), `play` and `pause` are the actions). The Sense/Net's fight screen is the Stack chrome's Script pane (the Script card, under Chromes), the Ono-Sendai's is the btop chrome's (the `ice.bas` tile, under Chromes; the terminal is its prompt) and the Hosaka's the suite's (the `PROC-7.BAS` Module window, under Chromes; its trace is the activity log); a chrome that dresses no Script pane shows the `prog` listing. The steps the interpreter says are logged as `LogKind::Program`; a RUN says nothing more than the program's own log line. The wireframe's damage is core too (`fight::broken`, `edges_left`, `break_order`) and tested there. The Ono-Sendai's fight view (`crates/app/src/fightview.rs`) is what the btop chrome's map pane shows in `Phase::Combat` (`ChromeView::network`; `ChromeView::combat_tab` brings it forward). It only reads the game, keeps its animation state in egui memory and its timings in `fightview::anim`, and runs programs through `Panes::act`.

## Terminals

`crates/term` is our own crate after egui_term's design, without a PTY: `LineEditor` (readline edits, kill ring, history, `Ctrl+R` search, Tab completion over words the caller supplies) and the `keys::bind` table are pure and tested; the egui widget (`widget::line`, feature `egui`) only maps key events and draws. It applies a frame's events in the order they arrived (`widget::edits` and `apply`, tested without a `Ui`), so on a slow frame text typed before Enter is still part of the line it runs. An Alt chord that also types a character (Option+B is `∫`) drops only that character, the text right beside the chord's key (after it natively, before it in the browser). A line longer than its room scrolls sideways to keep the cursor in view, readline's way, with `<` and `>` marking the hidden ends, so nothing is cut at the clip rect. A submit ends the line's frame: the edits after it wait for the next frame and are dropped if the line no longer has focus, so a command that opens a board or a modal doesn't leave its keys in the line. Esc is the line's too (its focus filter claims it, so egui doesn't drop the focus before the frame's typing is in): it leaves a search, or else the line lets go of the keyboard after the edits before it. NiGHTCOMM's page keys count only as a frame's first edit (`widget::edits`), so a slow frame's `ATDT 5550420` is typing. The run terminal's command line is one `LineEditor` on `App::term`, drawn by `Panes::prompt_as` for every chrome; its completions come from `panes::complete_run` and core's `command::VERBS`/`SLOT_VERBS`, and its history is saved (`Save::term_history`). The home Shell (both desktops) is another `LineEditor` on `Home::shell`, drawn by `Home::shell`; it completes from `hub::shell_complete`/`SHELL_VERBS` in core and saves `Save::shell_history` through `WbOut::ShellHistory`. A focus request waits for a frame where the ui is enabled. A new key is a line in `keys::bind`; if a browser would act on it, add it to `keys::BROWSER_CTRL` and `web/index.html`, which blocks those only while the game says something is typing (`window.ninseiTyping`).

## Sound

Sound is synthesized, never sampled. The modem handshake is built in core (`modem.rs`: `Handshake::new` lays out the timeline, `render` makes the samples; timings in `tuning.rs`). Dial screens print their lines from the same `Handshake`, so text and sound stay in step. Run sounds are **cues**: `Game::apply` compares before and after a successful action (`cue::cues`) and pushes `Cue`s onto `Game::cues` (capped; refused actions are silent; never touches the RNG); the app drains them each frame. Each cue's recipe is data: sound packs are files in `data/sounds/<id>.ron`, found by `build.rs` like boards (`Data::sounds`, `Data::sound_pack`); every pack must cover every cue (`SoundDef::validate`), and a deck's firmware names its pack (`FirmwareDef::sounds`), so a new OS's sounds are a new file. `SoundDef::render` synthesizes them. A pack file is `(cues: [...], music: [...])` (`cue::PackFile`): `music` is the run's soundtrack, at most one `music::RunTune` per network tier, each a cracktro-format `TuneDef` plus the `drop` track that falls silent under pressure; a tier or a whole pack with no music is silent (`Data::run_tune`). `music::validate` checks each tier against `hub/networks.ron`, each drop against the tune's tracks, and each loop against `music::MAX_LOOP_SECS` (a loop is the LCM of its tracks' lengths and is held in memory whole). Music is look: core decides what should play (`music::wanted` returns a `Wanted`: pack, tier, arrangement and the tune, while the screen is `JackIn` or `Run` and the phase is `Exploring`, `Combat` or `Encounter`; nothing at home, after a flatline or a jack-out) and how trace arranges it (`music::arrangement`, two coarse steps: the drop track goes at `MUSIC_DROP_AT`, the tempo rises by `MUSIC_TEMPO_BPM` at `MUSIC_TEMPO_AT`, all in `tuning.rs`); it reads the game and never touches it or the RNG, so the probe never hears it. `TuneDef::loop_render` renders exactly one cycle, no fade, as a bed (every track but the drop) and a stem (the drop track), a slice at a time (`LoopRender::work`, the same samples however it's sliced); notes still ringing at the end fold back into the start, so the loop never seams. `TuneDef::render_loop` is the same, all at once, and both share their per-track synth with `TuneDef::render`. `crates/app/src/sound.rs` only mixes and plays, through an `Output` (cpal natively, Web Audio in the browser, a logging stand-in in its tests), quiet if there's no device: a modem channel a hang-up can cut, a music channel that holds one cracktro tune or one run loop (bed and stem side by side, the stem behind a gain), plus cue voices that layer over both and play out. The app passes `wanted` to `Speaker::run_music` every frame: a new tune renders a slice a frame (the app keeps frames coming until it's ready) and starts when done; a drop step only fades the stem out or in, keeping the loop's place; a tempo step renders the new loop in the background and swaps it in at the same point in the music; a loop that fails to start is tried again. `Speaker::stop_music` stops only the run's tune, `stop_tune` only a cracktro's. `Save::sound` mutes everything, and turning sound back on starts the tune again. `Speaker::listen(n)` gives the last `n` samples of what's playing, mixed as the speaker mixes it: the run loop at `music_place` (its stem only while it isn't dropped; the bed and stem are `Arc`s shared with the output, so nothing is copied), cues and the modem by when they started on the frame clock (`Speaker::tick`), at the master level, and silence when sound is off. It reads what the speaker already holds, so both backends feed it alike; the playhead it reads is an atomic the cpal callback writes once a buffer (Web Audio's comes from the context's clock), so the audio thread never waits on it. `Save::volume` is one master level over the modem, the music and the cues (`Speaker::set_volume`): cpal multiplies it into the mix and Web Audio routes everything through a master `GainNode`, both easing to a new level so it never clicks; an output opens at the saved level, and at full it's left as it opens.
