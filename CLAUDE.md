# ninsei

Cyberspace hacking roguelike styled as a retro IDE. Rust workspace: `crates/core` (pure rules), `crates/term` (the terminals' line editor) and `crates/app` (eframe/egui + egui_dock).

## Design

How the game should look and feel lives in [`docs/design.md`](docs/design.md): the pillars, how theme, monitor and deck combine, and each deck's point of view. The **Ono-Sendai** is the hacker deck (Omarchy, btop, cyberpunk). The **Hosaka** is the corpo deck (a productivity suite). There are comps for both, and more decks are coming. Read it before building UI, and add a deck there before adding it to the data.

## Commands

| Purpose | Command |
|---|---|
| Run | `cargo run -p ninsei [-- <hexseed>]` |
| Tests | `cargo test --workspace` |
| Lint | `cargo clippy --workspace --all-targets` (keep it warning-free) |
| Format | `cargo fmt --all` |
| Balance probe | `cargo run --release -p ninsei-core --example balance [careers]` (single runs per tier and whole careers, by bots; in game: `probe [n]` in the home Shell) |
| Web build | `scripts/build-web.sh` (needs the wasm32 target and `wasm-bindgen-cli` matching Cargo.lock) |
| Web lint | `cargo clippy -p ninsei --target wasm32-unknown-unknown` |

CI (`.github/workflows/ci.yml`) runs fmt, clippy (native and wasm) and tests on every push; `pages.yml` deploys the web build on pushes to `main`.

## Working from issues

Features and bugs come in as GitHub issues (forms in `.github/ISSUE_TEMPLATE/`). One issue per PR; the PR body says `Closes #N` so merging closes it. Read the issue and its comments first, and ask in chat if it's ambiguous. Don't comment on issues unless asked. Bug reports carry a seed: replay it before fixing.

## Rules

- **Core never imports egui.** Rules, generation, BBS navigation and ANSI parsing live in `ninsei-core` and are tested headlessly. The app sends `Action`s to `Game::apply` and renders state; panes push requests and never mutate the game while drawing.
- **Content lives in `data/`, never in code.** Add warez/ICE/loot/BBS files there; `Data::validate` must catch any bad cross-reference.
- **Balance numbers live in `crates/core/src/tuning.rs`.** After changing them, run the balance probe; the `runs_always_end` test fails if a dumb bot always or never wins.
- **The probe plays the real game.** `crates/core/src/probe.rs` drives bots through `Save::dial`, `Game::apply`, `Save::record`, `Save::buy` and `Save::wardial`, never a model of the rules: spot checks per tier (a dumb bot and a competent one) and careers from a fresh save (climbing tiers, shopping in RIG, wardialing). `Probe` is resumable (`step` plays a few runs) so the home Shell's `probe [careers|stop]` can run it a little each frame in the browser; the CLI is the `balance` example. Same seed, same report, and its lines fit the Shell. When the game gains a way to progress (a shop, a source of numbers), teach the career bot to use it, or the probe stops telling the truth.
- **Every colour comes from the theme** in `data/themes.ron` (`Data::validate` checks them). One theme (`Save::phosphor`) colours both the desktop and runs; every theme must work in both. In a run that's the `Palette` (`crates/app/src/theme.rs`); on the desktop it's the `Desk` palette register in `home.rs`, loaded each frame from the desktop theme and read through `backdrop()`/`ink()`/`shadow()`/`accent()`/`muted()`/`fill()`. Never hard-code a colour in either. The BBS window's true CGA colours and the crash screen's red are the only exceptions.
- **Saves never break.** The hub's save (`crates/core/src/hub.rs`) is one versioned RON document. New fields get `#[serde(default)]` so old saves still load; bump `SAVE_VERSION` only for incompatible changes. An unreadable save starts a fresh hub, never a crash.
- **The hub's rules live in core** (`hub.rs`: save, screen flow, Shell commands); `workbench.rs`, `tiling.rs` and `crash.rs` only draw and route input. Desktop icons are pixel art in `data/hub/icons.ron`.
- **Desktops are front-ends on one home.** Each deck firmware names a `hardware::Desktop` (the deck's OS, named by `Desktop::name`: `Tiling` is AnarchyOS, `Workbench` is Desktop, `Liza` is Liza). `crates/app/src/home.rs` owns everything they share (the Shell, the tool bodies, the dial and scan clocks, `WbOut`); a desktop implements `DesktopView` and is listed in `Desktops`, so a new OS is a variant, a renderer and a registry entry. Layout and focus rules live in core (`desktop.rs`, e.g. `Tiling`, `desktop::search`) and are tested there; the tiling layout is saved on `Save::tiling`. Keys must work in a browser: AnarchyOS uses Esc as its leader, never Ctrl/Alt shortcuts.
- **Add-ons are data.** Desktop upgrades live in `data/hub/desktops.ron` (`AddonDef`, validated in `Data::validate`), each with an `AddonEffect`; owned ids are `Save::addons`, bought with `Save::buy_addon`, read with `Save::has_effect`. A new upgrade is a new effect plus its use in that desktop's renderer, sold in RIG for the desktops your decks run.
- **BBS screens are pipe-coded text, max 78x24**, enforced by `every_screen_fits_the_terminal` (every screen of every board).
- **Boards are folders.** Each BBS is `data/bbs/<id>/` (`board.ron` + `splash.txt`), found by `crates/core/build.rs`; nothing registers them. `Data::boards` holds them with the `default: true` board first. A run's board is `Game::board` (read it through `Game::bbs()`, never `data.boards[0]`), chosen by `Save::site_board`: a trait's `Board(id)`, else one of the boards for the tier picked by the phone number, else the default. Choosing a board must never touch the run's RNG before the network is generated. A board's look (`Look`: header style, colour roles, wording, l33t) is data; `bbs.rs` draws with the board's colours, never hard-coded pipe codes.
- **A BBS session reads a `Line`.** `bbs::Session` draws and navigates through the `Line` trait: a board reached in a run (`Game`) or called from home (`home_bbs::HomeCall`). New BBS features go through `Line`, never `&Game`. From home (`crates/core/src/home_bbs.rs`): boards are learned in a run (`Game::bbs_seen`, kept by `Save::record`) or by wardialing their number (`Answer::Board`); `Save::call_board` charges `call_cost`; listings and jobs are seeded from the save's key, the board and `Save::runs`, and `record` clears what was bought or taken. Jobs taken at home wait in `Save::pending` and ride into the run on their entry's network (`Kit::jobs`), where `Game::bring_jobs` picks targets with its own RNG after the network is built. Deck mods only sell in a run.
- **l33t goes through one translator** (`crates/core/src/leet.rs`, `leet::translate`). It's one character in, one out, so layouts keep their width; it leaves pipe codes, digits, bracketed hotkeys and 8.3 filenames alone. A board with `look.leet` applies it to every screen but the splash and the modem lines; an event opts in with `leet: true`.
- **Every encounter needs a `Leave` choice** (`Data::validate`), and `every_choice_in_every_event_resolves` must keep passing: no choice may leave the runner stuck in `Phase::Encounter`.
- **Sound is synthesized, never sampled.** The modem handshake is built in core (`modem.rs`: `Handshake::new` lays out the timeline, `render` makes the samples; timings in `tuning.rs`). Dial screens print their lines from the same `Handshake`, so text and sound stay in step. Run sounds are **cues**: `Game::apply` compares before and after a successful action (`cue::cues`) and pushes `Cue`s onto `Game::cues` (capped; refused actions are silent; never touches the RNG); the app drains them each frame. Each cue's recipe is data: sound packs are files in `data/sounds/<id>.ron`, found by `build.rs` like boards (`Data::sounds`, `Data::sound_pack`); every pack must cover every cue (`SoundDef::validate`), and a deck's firmware names its pack (`FirmwareDef::sounds`), so a new OS's sounds are a new file. `SoundDef::render` synthesizes them. `crates/app/src/sound.rs` only mixes and plays: a modem channel a hang-up can cut, plus cue voices that layer and play out (cpal natively, Web Audio in the browser), quiet if there's no device. `Save::sound` mutes everything.
- **The app runs native and in the browser.** No `std::time::SystemTime`, threads, files or `std::process` in code the web build reaches; gate native-only code with `#[cfg(not(target_arch = "wasm32"))]`.
- **A modal owns the keyboard.** Windows that take keys (BBS, talk) ignore input on the frame they open and call `stop_text_input` so the terminal can't eat their keys.
- **Programs are tracked by `Slot::uid`, not index**, wherever the UI holds on to one across frames: trades and sales reshuffle the HDD.
- **Two signing keys.** In a run, binaries are signed with the run's key (`Game::key`); in the stash, with the save's key (`Save::key`). Programs are re-sealed whenever they cross between home and a run (`Save::kit`/`Game::start` on the way in, `Save::record` on the way out); nothing else may re-sign a binary except optimize.
- **Networks are data.** Tiers, traits and companies live in `data/hub/networks.ron` (`NetworksDef::validate`). A trait is a `TraitEffect` that `Save::site_params` turns into `NetParams` (generation) or `RunMods` (ICE strength, trace %, pay %); add new effects there, not as special cases in the run. Default `NetParams` must keep generating the same networks for the same seed. A trait's `Shape` sets the topology (widths, cross links, chokepoints); tiers and the `Subnets` effect place subnet nodes.
- **Subnets are side trips.** Entering a `Subnet` node swaps in a smaller network (`Network::subnet`, seeded from the run and node) and parks the main one in `Game::outer`; the subnet's exit (the UPLINK) puts you back on the subnet node. Contracts always point into the main network: use `Game::root`/`root_at`, never `game.net`, for contract nodes.
- **Phone ranges are data too.** `data/hub/exchanges.ron` defines ranges (`RangeDef::validate`); `Drop::Hint(range)` teaches one, from loot, BBS files or encounters, and `Data::validate` rejects hints at unknown ranges. A wardial block always answers the same way for a save (seeded from `Save::key`, range and block), so results never depend on when you scan.
- **The network map has two views, both themed.** `crates/app/src/netmap.rs` holds what both share (fog, targets, tags, clicks, the hint) and hands off to `netmap_iso.rs` (wireframes over a grid) or `netmap_draft.rs` (a flat technical drawing), picked by the deck's firmware (`Save::firmware_def(..).map`). Shapes and symbols per node kind are data (`data/netmap.ron`, `MapStyleDef::validate`); meshes, the isometric camera (`Iso`) and node placement live in core (`netview.rs`) and are tested there. Map colours come from the palette like everything else: grid `faint`, wires `fg`, fills `dim`, highlights `bright`. Map animation (derez bursts, the jack-in sweep, trace pressure, hover) lives in `netmap::Anim`, remembered in egui's memory rather than the game, with every timing in `netmap::anim`; the hop trail comes from `Game::travelled`.
- **Looks are hardware.** Monitors and decks live in `data/hub/hardware.ron` (`HardwareDef::validate`); what you own and what's plugged in are on `Save` (`monitors`/`monitor`, `decks`/`deck`/`firmware`), fixed up by `Save::ensure_hardware`. The monitor picks the CRT preset (`Save::display_id`) and, if mono, locks the theme: any theme change goes through `Save::theme_blocker`. A deck's firmware is built from named parts (`netview::MapView`, `hardware::Chrome`, `hardware::Desktop`, and a sound pack); read the active one with `Save::firmware_def`, and add a new look as a new part (enum variant + renderer) that firmware entries can name, never as a special case on a deck id. Hardware is look and feel only: no stats.
- **Graphs read history; history watches the rules.** `Game::history` (`crates/core/src/history.rs`) is filled by `Game::apply` from before/after snapshots: samples per action, trace per hop, the fight's ICE strength and turn rows, programs run. It never changes play (the balance probe must not move). Dot-graph maths is `history::plot`, tested in core; the font has no braille, so the app paints the dots. The btop chrome (`crates/app/src/btop.rs`, `Chrome::Btop`) keeps its timings in `btop::anim` and colours its gradients with `btop::ramp` (`faint → dim → fg → bright`).
- **Chromes are plug-ins.** A firmware's `hardware::Chrome` picks how the run screen is dressed; `crates/app/src/chrome.rs` maps it to a `ChromeView` (`chrome::view`): one method per pane, plus tab titles, menus (arranged from shared `MenuPart`s), the status line, an optional bar under the panes, keys, an overlay and the default layout. Every method defaults to Classic, so a new chrome is a `Chrome` variant plus a `ChromeView` that overrides only what it changes. Never test the chrome in a pane; ask the view. `btop.rs` (`Chrome::Btop`) and `suite.rs` (`Chrome::Suite`, the Hosaka) are the two so far; the suite's rules (sheet sorting, formulas, axes, work-order totals, dialogs via `suite::Watch`) live in core's `suite.rs`.
- **Fights have a view; the preview is the rule.** `Game::preview(slot)` (`crates/core/src/fight.rs`) says what running a program would do now or why it can't, and `Action::Run` resolves through it, so a hint can never disagree with what happens. The wireframe's damage is core too (`fight::broken`, `edges_left`, `break_order`) and tested there. The Ono-Sendai's fight view (`crates/app/src/fightview.rs`) is what the btop chrome's map pane shows in `Phase::Combat` (`ChromeView::network`; `ChromeView::combat_tab` brings it forward). It only reads the game, keeps its animation state in egui memory and its timings in `fightview::anim`, and runs programs through `Panes::act`.
- **Panes are modular, and secondary panes are owned.** `panes::Tab` lists every pane: `Tab::CORE` are always there; `Tab::SECONDARY` pairs each extra pane with its id in `data/hub/panes.ron` (`PaneDef`). A secondary pane is available when bought in RIG (`Save::buy_pane`, `Save::panes`) or bundled with the firmware (`FirmwareDef::panes`); read it with `Save::has_pane`. A new pane is a variant, an id, a catalog entry and a renderer, dressed by each chrome (`ChromeView::net` is the pattern). The default layout is the chrome's (`ChromeView::default_layout`) with the panes the player has; the player's layout is saved per deck firmware in `Save::layouts` as opaque RON the app writes (`Save::set_layout`/`layout`, core never parses it). Anything that won't read back or lacks a core pane falls back to the default, and panes the player doesn't have are dropped (`parse_layout`).
- **Terminals edit lines with `ninsei-term`.** `crates/term` is our own crate after egui_term's design, without a PTY: `LineEditor` (readline edits, kill ring, history, `Ctrl+R` search, Tab completion over words the caller supplies) and the `keys::bind` table are pure and tested; the egui widget (`widget::line`, feature `egui`) only maps key events and draws. The run terminal's command line is one `LineEditor` on `App::term`, drawn by `Panes::prompt_as` for every chrome; its completions come from `panes::complete_run` and core's `command::VERBS`/`SLOT_VERBS`, and its history is saved (`Save::term_history`). The home Shell (both desktops) is another `LineEditor` on `Home::shell`, drawn by `Home::shell`; it completes from `hub::shell_complete`/`SHELL_VERBS` in core and saves `Save::shell_history` through `WbOut::ShellHistory`. A focus request waits for a frame where the ui is enabled. A new key is a line in `keys::bind`; if a browser would act on it, add it to `keys::BROWSER_CTRL` and `web/index.html`, which blocks those only while the game says something is typing (`window.ninseiTyping`). Chrome never gives a page Ctrl+W/T/N, so each needs another key.
- **Browser keys.** F5, F6, F7, F11 and F12 belong to the browser. `web/index.html` blocks the defaults of F1, F3 and F10 so the suite's legend can use them; add a key there before using it.
- **Damage glitches are visual only.** Core gives the level (`glitch::level`, `Game::glitch`), the last hit (`History::last_hit`) and width-keeping text corruption (`glitch::corrupt`); the app (`crates/app/src/glitch.rs`) scales a *copy* of the CRT preset for the shader (plus `u_tear`), draws the hit flash and the no-shader fallback, and hands the corruption rate to the panes, which only garble log text, never meters or numbers. The mouse keeps the preset's geometry, flicker stays capped (`glitch::tune::FLICKER_MAX`), and `Save::glitches` (on, reduced, off) is honoured everywhere. All strengths live in `glitch::tune`.
- **Run vs home.** In a run, `Action::Patch`/`Optimize` only work at a BBS (`Game::compile_blocker`). Hub tool windows (`hubtools.rs`) never touch the save directly: they emit `WbOut`s that the app applies through `Save`'s methods.
- **A program's stats come from its 32-byte binary** (`crates/core/src/binary.rs`), never from `WarezDef` after creation. A slot never holds an invalid binary: `Action::Patch` runs `binary::check` first. Every factory program must fit the budget rule; `Data::validate` enforces it.
- **The CRT is a shader, its presets are data.** `crates/app/src/crt_gl.rs` is one glow `PaintCallback` over the frame (copy, burn-in, CRT pass); presets live in `data/displays.ron` (`DisplayDef::validate`, values 0..=1, theme must exist). The glass geometry is `display::screen_to_content` in core, and `raw_input_hook` maps pointer and touch input through it, so the shader and the hit-testing must use the same curve: change both together. If the shader fails to start, `crt.rs`'s flat overlay is the fallback.
